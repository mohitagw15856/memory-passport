# ADR-001: Markdown with YAML frontmatter, not JSON

**Status:** accepted · **Date:** 2026-09-22 · **Deciders:** mohitagw15856

## Context

memory-passport needs one on-disk format that every AI product can export to and import from. The obvious candidates were:

1. **JSON** (one document, or one file per subject) with a JSON Schema.
2. **YAML** throughout.
3. **SQLite**.
4. **Markdown files with YAML frontmatter**, one file per subject, facts as tagged bullet lines.

The format has to serve three readers at once: a person in a text editor, a language model given the file in a prompt, and a tool doing validation, merge and diff. It also has to survive being pasted into a chat box, which is how most products will actually receive it, because only one of them (Claude) has a memory import at all.

## Decision

Markdown files with YAML frontmatter (option 4). The structured part (name, description, sources, aliases, updated, kind) lives in frontmatter and is validated by a JSON Schema. The data (facts) lives in the body as bullet lines with a provenance tag. Anything else in the body is preserved and ignored.

## Why not JSON

- **A person cannot comfortably edit it.** The whole point is that you own this and can fix a wrong fact with a text editor. Quoting, escaping and trailing commas make that a chore, and a single typo makes the file unreadable rather than slightly wrong.
- **Models read prose better than structure.** Pasting a markdown file into ChatGPT or Claude works as-is. Pasting JSON works too, but wastes tokens on syntax and pushes the model to reply in JSON.
- **Diffs are worse.** A one-fact change in a JSON array often re-indents or re-orders siblings. A one-fact change in a bullet list is one line.
- **Merging is worse.** Git conflict markers inside JSON produce an unparseable file that no tool can partially read. Conflict markers inside markdown leave every other line readable, and the spec turns them into a validation error rather than a parse failure.
- **JSON has no comments.** The per-fact source annotation is an HTML comment precisely so that it is invisible in rendered markdown and trivially strippable for paste-export.

## Why not pure YAML

YAML for the whole file would keep it editable, but a list of facts in YAML is either a list of strings (losing the provenance tag as structure) or a list of mappings (back to the verbosity of JSON). Whitespace sensitivity also bites people editing by hand. YAML is used only in the small, flat frontmatter block, where its readability wins and its footguns are avoided by the schema forbidding unknown keys and requiring `updated` to be a quoted string.

## Why not SQLite

Not human-readable, not pasteable, not diffable in git. It would be the right choice for a product's internal store, and the wrong choice for the thing that moves between products.

## Consequences

- The format cannot express structured values (a `birthday:` field) or typed relationships between subjects. This is accepted; see SPEC.md §12.
- Parsing is a small regex over lines rather than `json.load`. That is more code in the toolkit and less in every consumer, which is the right trade.
- Frontmatter is closed (`additionalProperties: false`) so that products cannot smuggle their own fields back in. A product wanting to preserve extra metadata should keep it on its own side, keyed by the file's `name`.
- The JSON Schema still exists. It validates the frontmatter and gives implementers in other languages a precise target without reading prose.
